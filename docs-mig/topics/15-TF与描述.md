### 1.2 `tf_description.hpp` 定义的 TF 树（v2）

`tf_description.hpp` 已包含 `RawImu`（第 40–42 行 Link、第 84–88 行 `Joint<BaseLink, RawImu>`）。
TF 树（`Joint<>` 的 `Parent` 决定）：

```
base_link
├── gimbal_center_link           (Translation, Parent=BaseLink)
│   └── yaw_link                 (AngleAxis Z, Parent=GimbalCenterLink)
│       └── pitch_link           (AngleAxis Y, Parent=YawLink)
│           ├── muzzle_link      (Translation, Parent=PitchLink)
│           ├── transmitter_link (Translation, Parent=PitchLink)
│           ├── camera_link      (Isometry,    Parent=PitchLink)
│           ├── odom_imu         (Quaternion,  Parent=PitchLink)
│           └── viewer_link      (AngleAxis Y, Parent=PitchLink)
├── raw_imu                      (Quaternion,  Parent=BaseLink)
├── left_front_wheel_link        (Isometry + rot, Parent=BaseLink)
├── left_back_wheel_link         (Isometry + rot, Parent=BaseLink)
├── right_back_wheel_link        (Isometry + rot, Parent=BaseLink)
└── right_front_wheel_link       (Isometry + rot, Parent=BaseLink)
```

`JointCollection`：
- `Tf`（第 192–194）：`GimbalCenterLink, YawLink, PitchLink, MuzzleLink, TransmitterLink, CameraLink, OdomImu, RawImu, 4 轮, ViewerLink`
- `InfantryTf`（196–198）：同上但**去掉 `RawImu`**
- `HeroTf`（200–202）：同 `Tf`（含 `ViewerLink`、`RawImu`）
- `AutoAimTf`（204）：`MuzzleLink, TransmitterLink, CameraLink, OdomImu`

未使用项：`OmniLinkLeftFront/RightFront/Left/Right`（60–74）四个 Link 有定义，
但**没有任何 `fast_tf::Joint<>` 特化、也不在任何 collection 中**（两版相同）。

已有 quirk（v2/v3 相同）：`LeftBackWheelLink`/`RightBackWheelLink`/`RightFrontWheelLink`
的 Link 基类是 `fast_tf::Link<LeftFrontWheelLink>`（第 50/53/56 行，疑似笔误），
仅影响 tag 基类，未在比对范围内发现功能问题。

### 1.3 v2 的 TF 使用点

## 4. 迁移方案（以 v3 为骨架）

`rmcs_description` 与 `fast_tf` 的差异极少，迁移工作量集中在**消解 T4/T5 的类型冲突**与
**决定是否启用 sentry_description**。

1. **保留 v3 现状**：`tf_description.hpp` 不动（两版相同）；`fast_tf` 改动为格式化，无需回迁。
2. **消解 T4/T5（重点）**，二选一：
   - **方案 A（推荐）**：让哨兵硬件改用 `sentry_description.hpp`（`SentryTf`），
     并让所有依赖双 yaw/升降的组件统一使用 `sentry_description::Tf`；
     `EccentricDualYaw` 与 `hardware/dual_sentry.cpp` 类型一致后接线。
   - **方案 B**：把 `tf_description.hpp` 扩展为同时含哨兵链路的**单一** `Tf`
     （合并 `BottomYawLink/TopYawLink/OdomGimbalImu`），删除 `sentry_description.hpp` 的独立 `Tf`，
     避免同名类型冲突。
   - 无论哪种，都要保证**同一编译单元只包含一个定义 `rmcs_description::Tf` 的头**。
3. **哨兵 TF 树落地上位机**：v3 `sentry.yaml_`（legacy）是启用参考；确认
   `EccentricDualYaw` 所需的 `/gimbal/top_yaw/{angle,velocity}`、`/gimbal/bottom_yaw/{angle,velocity}`、
   `/gimbal/pitch/{angle,velocity}` 等接口由硬件产出（`eccentric_dual_yaw.cpp:176–192` 声明）。
4. **urdf**：若需 rviz 可视化哨兵/raw_imu，需新增/扩展 xacro（当前两版 urdf 都没有）。属可选增强。
5. **`fast_tf` dummy**：若交叉编译/CI 依赖 `fast_tf_dummy` 生成编译数据库，需在 v3 恢复等价目标
   （或在别处放置一个包含 `fast_tf.hpp` 的 `.cpp`）。

## 7. 备注与未决问题

- **背景更正**：任务描述中「v3 新增 RawImu link 与 TF joint」经核对**不成立**——
  `tf_description.hpp` 两版 md5 完全一致（`3e3f6775…`），`RawImu` 及其 `Joint` 在 v2 即存在。
  同理「urdf 差异」亦**不存在**（urdf/launch/rviz 全部相同）。
  真实差异只有两项：**新增 `sentry_description.hpp`** 与 **`fast_tf` 去掉 dummy 目标/格式化**。
- **未决**：`sentry_description.hpp` 与 `tf_description.hpp` 的类型重叠（T4）目前未在任何现役配置中同时实例化，
  故「是否已经会编译失败」**未核实**（需要实际接线后验证）；
  但两者定义同名 `rmcs_description::Tf`/`YawLink` 是客观事实，必须在其被同时使用前解决。
- **未决**：`InfantryTf` 不含 `RawImu`，而 `Tf`/`HeroTf` 含 `RawImu`；是否有意为之、由谁使用 `InfantryTf`
  在 v3 现役代码中**未核实**（grep 未见 `/tf` 使用者显式声明 `InfantryTf`）。
- `fast_tf` 的 `joint_collection.hpp`/`rcl.hpp` 空格差异可能因 clang-format 版本不同重新出现，
  合并时注意避免无意义 diff。

  与 `rmcs_description::SentryTf` **无关**，勿混淆。
